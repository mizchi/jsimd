# BitHistogram32

A streaming positional-popcount accumulator for `Uint32Array` data. It returns 32 counters: output
lane `i` is the number of input words whose bit `i` is set.

```ts
import { BitHistogram32, bitHistogram32 } from "@mizchi/jsimd/bit-histogram32";

const output = new Uint32Array(32);
bitHistogram32(new Uint32Array([1, 3, 0xffff_ffff]), output);

using histogram = new BitHistogram32();
histogram
  .add(firstChunk)
  .add(secondChunk)
  .writeInto(output);
histogram.reset();
```

`BitHistogram32` keeps only its 32 counters in Wasm memory; input chunks are copied for each `add`.
Bind it with `using` so the counter allocation returns to the module-local reuse pool. The running
`length` is limited to `2^32 - 1`, preventing unsigned counters from silently wrapping. The one-shot
`bitHistogram32` helper creates and releases the same accumulator internally.

## Algorithm

Each input `u32` is broadcast into a SIMD register. Two `i8x16.swizzle` operations replicate its
four bytes into the low and high groups, and lane-specific bit masks expand them into 32 byte-sized
0/1 counters. Byte accumulators flush after 255 words, widening through `i16x8` into the 32 resident
`u32` counters before a lane can overflow.

This is a compact Wasm-oriented positional-popcount kernel, not a port of a specific native
implementation. For broader native techniques and workload analysis, see
[Faster Positional-Population Counts](https://arxiv.org/html/2412.16370v1).

## Performance and trade-offs

Recorded with Vitest 4.1.11 / Node 24 / Apple M5 over 262,144 words. Both Wasm timings include input
copy and all 32 output counters.

| input                  | copy-inclusive SIMD | best JavaScript | result       |
| :--------------------- | ------------------: | --------------: | :----------- |
| dense pseudo-random    |            0.301 ms |        4.350 ms | 14.4x faster |
| sparse three-bit flags |            0.293 ms |        1.363 ms | 4.66x faster |

The dense JavaScript baseline tests all 32 positions. The sparse baseline iterates only set bits, so
the reported comparison uses the best algorithm for each input. Reusing a resident histogram changed
0.301 ms to 0.293 ms in the dense case; input copy and the kernel dominate, not ownership.

This remains a bulk API. At 64 dense words it was 1.91x faster, but for one word JavaScript was
9.03x faster because object/allocation and JS/Wasm boundary costs dominate. Streaming is useful for
composing many chunks without materializing and merging 32-counter arrays, not for recounting
unchanged data.

```sh
pnpm bench:record:bit-histogram32
pnpm bench:compare:bit-histogram32
```

## Standalone build size

The isolated Vite fixture emits one 0.56 kB Wasm asset (0.27 kB gzip) and a 4.97 kB minified JS
wrapper (2.17 kB gzip). It emits no other entrypoint's Wasm.

Files:

- `mod.ts`: streaming ownership, copy-inclusive helper, validation, and output contract
- `kernels.wat`: byte expansion, bounded byte counters, and widening flush
- `kernels.d.wasm.ts`: typed Wasm module contract
- `kernels.wasm`: generated by `wasm-tools strip`, validated, and Git-ignored
