# BlockedBloomFilterU32

A mutable probabilistic filter for bulk `Uint32Array` membership checks. It has no false negatives:
an output zero proves that a key is absent, while an output one means that an exact structure still
has to verify the candidate.

```ts
import { BlockedBloomFilterU32 } from "@mizchi/jsimd/blocked-bloom-filter";

const keys = Uint32Array.of(10, 20, 30, 40);
using filter = BlockedBloomFilterU32.from(keys, 12);

const queries = Uint32Array.of(10, 11, 20, 21);
const possible = new Uint8Array(queries.length);
filter.mayContainMany(queries, possible); // 2
possible; // Uint8Array [1, 0, 1, 0]
```

Declare the filter with `using`. Scope exit returns its Wasm allocation to the module's reuse pool.
`addMany()` mutates the filter, `clear()` resets it, and `merge()` unions filters with matching
block counts. There is intentionally no point `has()` method: the performance contract is a batched
negative lookup followed by exact verification of only the candidates.

## Layout

The bit array is divided into 128-bit blocks. One mixed hash chooses a block; a separately remixed
hash chooses one bit in each of its four 32-bit lanes. Insertion loads one `v128`, ORs the four-bit
mask, and stores it. Lookup uses `v128.and`, `i32x4.eq`, and `i32x4.all_true`. Consequently each key
touches one 16-byte block and always uses four probes.

Blocked Bloom filters were introduced to localize each operation to one memory block; see Putze,
Sanders, and Singler's
[“Cache-, Hash- and Space-Efficient Bloom Filters”](https://ae.iti.kit.edu/english/1268.php).
[Blocked Bloom Filters with Choices](https://doi.org/10.4230/LIPIcs.SEA.2025.25) gives a recent
analysis of blocked-filter false-positive trade-offs. This implementation uses one Wasm `v128`
rather than a CPU cache-line-sized block and does not implement multiple block choices.

At 12 requested bits/key, 262,144 inserted keys occupy 393,216 bytes (exactly 12 bits or 1.5 bytes
per key). The recorded deterministic workload produced 9,525 false positives among 1,048,512 known
misses: 0.908%.

## Performance characteristics

Recorded with Vitest 4.1.11 / Node 24 / Apple M5 over 262,144 resident keys and roughly 1,048,576
queries. `mayContainMany()` includes copying the query keys into Wasm and its byte mask back out.
The end-to-end rows include exact `Set.has` verification for every Bloom candidate.

| workload     | Bloom + `Set` | direct `Set.has` | result                  |
| :----------- | ------------: | ---------------: | :---------------------- |
| known misses |      9.316 ms |        51.133 ms | Bloom 5.49x faster      |
| 90% misses   |     11.162 ms |        48.830 ms | Bloom 4.37x faster      |
| 50% misses   |     22.602 ms |        37.092 ms | Bloom 1.64x faster      |
| 10% misses   |     29.580 ms |        30.896 ms | near parity             |
| all hits     |     32.467 ms |        26.643 ms | direct Set 1.22x faster |

The isolated Wasm Bloom scan took 3.502 ms versus 39.705 ms for the equivalent scalar typed-array
filter. Construction took 0.831 ms versus 8.140 ms for scalar Bloom and 17.457 ms for `Set`.

This structure is not always faster than JavaScript. It adds work to every true hit and false
positive, so hit-heavy workloads should query the exact `Set` directly. The crossover depends on
engine, hash distribution, exact structure, and configured bits/key; the recorded 10%-miss case was
already near parity. It also cannot enumerate keys or replace an exact collection. Use it when a
large batch is expected to contain many misses and the exact lookup is expensive enough to skip.

## Standalone build size

The isolated Vite 8.2 production fixture emits a 5.98 kB minified JavaScript wrapper (2.49 kB gzip)
and one 0.51 kB Wasm asset (0.37 kB gzip). It does not emit another jsimd Wasm module.

Benchmark source and the committed baseline are under
[`experiments/blocked-bloom-filter`](../../experiments/blocked-bloom-filter).

Files:

- `mod.ts`: public contract, allocator, bulk copies, ownership, and validation
- `kernels.wat`: hashing, blocked insertion/query, and SIMD union
- `kernels.d.wasm.ts`: typed Wasm module contract
- `kernels.wasm`: generated by `wasm-tools strip`, validated, and Git-ignored
